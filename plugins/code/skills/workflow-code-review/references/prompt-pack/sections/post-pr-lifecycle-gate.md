# Post-PR Lifecycle Gate

After the finalization subagent raises one or more PRs for a work item, start this gate immediately for that work item. Do not wait for every work item in the goal to raise PRs.

PR lifecycle monitoring must be delegated to a bounded `post-pr-lifecycle` subagent for that work item. The orchestrator must not keep itself or any subagent alive solely to poll GitHub. Each `post-pr-lifecycle` invocation performs one inspection pass, returns the current state, and exits.

The orchestrator and subagents must not merge PRs unless the user explicitly asks them to merge.

## Merged PRs End the Lifecycle Gate

A merged PR is terminal lifecycle evidence: the human already accepted the PR, so the pre-merge readiness machinery has nothing left to prove. When the user reports that a PR is merged, or any inspection observes GitHub PR state `MERGED`, the orchestrator must:

1. Confirm the merge with one cheap read, for example `gh pr view <pr-url> --json state,mergedAt,mergeCommit`. Do not launch a bounded `post-pr-lifecycle` subagent just to confirm a reported merge.
2. Record the evidence with `{{WORKFLOW_CLI}} pr merge-record --goal-slug <goal-slug> --work-item-id <work-item-id> --pr-url <pr-url> --merged-at <merged-at-iso> [--merge-commit-sha <sha>]`.
3. Rerun `{{WORKFLOW_CLI}} next`. The runner skips the rest of the PR lifecycle machinery for that work item and routes directly to closeout.

After merge evidence is recorded, do not launch further bounded `post-pr-lifecycle` passes to re-check routine PR readiness, do not wait for `pr.nextCheckAfter`, do not refresh Fresh PR Lifecycle Evidence for the merged head, and do not treat a stale `waiting_on_ci`, `waiting_on_review`, or `needs_fix` ledger entry as a reason to wait, poll, or launch a fix worker. A deleted remote branch after merge is expected, not a blocker. Only the closeout gates remain: manual loop closeout, quality incidents, knowledge curation, and the completion gates, plus any unresolved user-reported manual regression or manual testing debt, which merging does not resolve.

The one exception is an unresolved user-reported manual regression, which merging does not resolve. Its remediation loop still runs after merge, including the single bounded verification pass the runner emits once a fix is pushed (`pr.manualRegressionStatus: "fix_pushed"`). That pass confirms the fix against the still-queryable merged PR, since GitHub keeps the PR and its checks after merge, so the orchestrator can record the regression resolved and the item can then close out. Without it, a merged item with a pushed regression fix would block on completion with no autonomous path to resolution. A merged PR routes straight to closeout only once no unresolved regression remains.

## User-Reported Manual Regressions After PR Readiness

If the user reports that manual/local validation failed after a PR was raised, marked ready, or previously considered complete, treat it as a post-PR remediation signal, not as permission for the orchestrator to patch code directly.

The orchestrator must:

1. Record the report with `{{WORKFLOW_CLI}} pr manual-regression --goal-slug <goal-slug> --work-item-id <work-item-id> --status reported --summary "<reproduction>"`, which sets `pr.manualRegressionStatus: "reported"`, `pr.manualRegressionReportedAt`, and `pr.manualRegressionSummary` and appends the `manual_regression_reported` status event. Do not hand-patch these `pr.manualRegression*` fields with raw `ledger upsert`.
2. Rerun `{{WORKFLOW_CLI}} next`; the runner routes `reported` regressions to `launch_pr_followup_fix`. The runner emits this follow-up even when the last PR lifecycle snapshot is `ready_for_human_merge`, so there is no need to invalidate the prior ready evidence by hand.
3. Launch or resume a bounded fix subagent with the existing worktree, branch, PR URL, regression summary, and any user-provided reproduction evidence. Do not inspect source code for the fix in the orchestrator.
4. Instruct the fix subagent to add or update automated coverage that would have caught the regression when existing repo infrastructure supports it. If the regression concerns user-visible state/status/lifecycle/rendering, the fix must update the User-Visible State Matrix evidence and cover stale or mixed state combinations, precedence rules, initial-load behavior, refresh/repair behavior, and the actual renderer/consumer when practical. For UI layout, styling, or visual rendering regressions, require rendered-screen validation with existing repo tooling or a concrete manual-testing-debt classification for any visual risk that cannot be automated.
5. After the fix subagent pushes a fix commit, record `{{WORKFLOW_CLI}} pr manual-regression --goal-slug <goal-slug> --work-item-id <work-item-id> --status fix_pushed`, then launch a bounded post-PR lifecycle pass.
6. Record `{{WORKFLOW_CLI}} pr manual-regression --goal-slug <goal-slug> --work-item-id <work-item-id> --status resolved` (which sets `pr.manualRegressionStatus: "resolved"` and `pr.manualRegressionResolvedAt`) only after the bounded post-PR lifecycle pass confirms the latest head SHA is ready for human merge and the fix evidence includes validation for the reported regression.
7. If remediation cannot proceed (for example the regression is blocked on an external dependency, missing access, or a decision the user must make), record `{{WORKFLOW_CLI}} pr manual-regression --goal-slug <goal-slug> --work-item-id <work-item-id> --status blocked --summary "<blocker>"` (which sets `pr.manualRegressionStatus: "blocked"`). The runner routes this to a blocked action and the completion gate keeps the work item open until it is resolved; report the blocker to the user with evidence.
8. If the fix subagent says the regression proves the approved plan was wrong or incomplete, route to plan revision and failure intake instead of applying superficial patches.

## Fresh PR Lifecycle Evidence

The bounded `post-pr-lifecycle` result is the only source of truth for PR readiness and PR waiting state.

The orchestrator must not describe a PR as done, ready, waiting on review, waiting on branch protection, green, or having no autonomous work remaining unless it has a current bounded `post-pr-lifecycle` result for the PR's latest head SHA.

A current result must include:

- PR URL
- latest head SHA inspected
- aggregate checks state for the latest head SHA, from a full audit of every check run, check suite, and status context, plus the count of any suites classified as inert app placeholders; not per-check rows
- review state covering review comments, inline comments, requested changes, and unresolved threads
- review inspection timestamp and latest review activity timestamp
- unresolved thread count, actionable current-head comment count, and outdated handled comments without threaded replies or explicit audit evidence count
- reply-placement and thread-resolution audit state, reported as `passed`, `failed`, `not_applicable`, or `unknown`
- AGENTS.md rule-assessment state for every valid review comment addressed by this workflow, including valid comment count, handled comment count, missing assessment row count, and state `passed`, `missing`, `incomplete`, `not_applicable`, or `blocked`
- draft/ready state
- manual testing debt state and whether any debt is unresolved or blocked_external
- returned lifecycle state: `ready_for_human_merge`, `needs_fix`, `needs_plan_revision`, `waiting_on_ci`, `waiting_on_review`, or `blocked`
- `inspected_at` timestamp

This full readiness packet is required only when the returned lifecycle state is `ready_for_human_merge`, `waiting_on_review`, or `waiting_on_ci`. For `needs_fix`, `needs_plan_revision`, or `blocked`, the required return is the conclusion, the blockers, and whatever evidence was actually gathered; missing readiness counts are not a defect there, and the orchestrator must not resume a worker solely to backfill readiness counts on a `needs_fix` conclusion. Route the fix instead.

CI/branch-protection evidence alone is never enough. If the latest known evidence is missing, stale, for a different head SHA, lacks review-comment/thread inspection, lacks structured thread/reply audit counts, or has latest review activity newer than the last review inspection, the orchestrator must launch one bounded `post-pr-lifecycle` pass before reporting PR state or concluding no autonomous work remains. This is not polling; it is the required one-pass gate for truthful status.

`waiting_on_review` is allowed only after the bounded pass has inspected review comments, requested changes, and unresolved threads and found no actionable comment, requested change, unresolved handled thread, reply-placement failure, draft-state blocker, failing check, or pending check that is not explicitly classified as an inert app placeholder check suite. Use `needs_fix`, `needs_plan_revision`, `blocked`, or `waiting_on_ci` instead when any of those conditions exists. Do not use `waiting_on_review` to mean "comments have not been checked yet."

GitHub `isOutdated: true` means only that a comment's line anchor no longer maps to the latest diff. It does not mean the review concern was addressed, replied to, or resolved. If the workflow handled an outdated comment by changing code or deciding it is not applicable, the lifecycle evidence must include a threaded reply or explicit audit row explaining why no reply/resolution is needed. Outdated handled comments without that evidence block PR readiness.

The orchestrator must:

1. Assign a unique `post-pr-lifecycle` `status_file` for the work item and launch a bounded `post-pr-lifecycle` subagent with the PR URL or URLs, worktree path or paths, branch name or names, and any reply metadata returned by prior fix subagents.
2. Continue unrelated planning, execution, or finalization work while the bounded `post-pr-lifecycle` subagent runs. Do not block unrelated work items waiting for PR review comments.
3. For the initial post-PR lifecycle inspection immediately after PR creation, do not pass `execution_loop_id` and do not create a manual loop. The execution loop should already be terminal because the PR was raised. If this inspection is a re-check after an active PR remediation pass, pass the current `pr_followup_loop_id` so the subagent can submit loop events for that follow-up pass.
4. After every bounded `post-pr-lifecycle` result, record the worker's status file with `{{WORKFLOW_CLI}} pr lifecycle-ingest --goal-slug <goal-slug> --work-item-id <work-item-id> --status-file <status_file>`, which updates the ledger with `pr.lifecycleHeadSha`, `pr.lifecycleState`, `pr.checksState`, `pr.reviewState`, `pr.draftState`, `pr.reviewInspectionAt`, `pr.latestReviewActivityAt`, `pr.unresolvedThreadCount`, `pr.actionableCurrentHeadCommentCount`, `pr.outdatedHandledWithoutReplyCount`, `pr.replyPlacementAuditState`, `pr.threadResolutionAuditState`, `pr.validReviewCommentCount`, `pr.handledReviewCommentCount`, `pr.agentsRuleAssessmentState`, `pr.agentsRuleAssessmentMissingCount`, `pr.nextCheckAfter`, and the latest PR URL/head SHA evidence returned by the subagent. Do not hand-patch these lifecycle fields with raw `ledger upsert`. For `ready_for_human_merge`, run `{{WORKFLOW_CLI}} gate --goal-slug <goal-slug> --work-item-id <work-item-id> --gate pr_lifecycle_ready` before recording PR-ready status. If the gate fails, treat the lifecycle evidence as incomplete and do not mark the PR ready.
5. If the bounded `post-pr-lifecycle` subagent returns `ready_for_human_merge`, first verify its returned evidence satisfies Fresh PR Lifecycle Evidence for every PR latest head SHA and that manual testing debt is not `unresolved` or `blocked_external`. If `pr.manualRegressionStatus` is `fix_pushed`, verify the fix evidence includes validation for the reported regression, then record `{{WORKFLOW_CLI}} pr manual-regression --goal-slug <goal-slug> --work-item-id <work-item-id> --status resolved` to set `pr.manualRegressionStatus: "resolved"` and `pr.manualRegressionResolvedAt`; if that evidence is missing, keep the lifecycle in `needs_fix`. Then record an orchestrator status event with `phase: pr_ready_for_human_merge`, `status: completed`, the relevant `pr_url` values, latest head SHA values, and a concise review-thread/comment summary. If a `pr_followup_loop_id` is active, add a final loop event that the PR gate is green/ready, call `complete_loop` with the primary PR URL, primary branch, and a summary that includes all PR URLs for cross-repo work, then call `get_loop` and verify the follow-up loop is terminal. Append an orchestrator status event with `phase: manual_loop_terminal_verified`, `status: completed`, `pr_followup_loop_id`, `loop_status`, and `loop_terminal_verified: true`. Update the ledger `loops` array with the terminal PR follow-up loop evidence. If the follow-up loop remains active or verification fails, keep the work item blocked on loop closeout instead of marking it complete.
6. If it returns `needs_fix`, create a short-lived PR follow-up loop per `sections/closedloop-manual-loop-visibility.md`, unless a PR follow-up loop is already active for the same remediation pass. Record the PR follow-up loop ID in the ledger. Then resume the original implementation/execution subagent for that work item when it is still available. If it cannot be resumed, launch a replacement implementation-fix subagent for the same worktree path and branch. Pass the `pr_followup_loop_id` to the fix subagent. The orchestrator must include the `Required AGENTS.md Rule Assessment` block from this section explicitly in the worker handoff, including the requirement to perform a per-comment assessment and return the assessment summary counts and status event. The orchestrator must not patch code or reply to PR comments directly; it only triages, delegates, audits returned evidence, and reports.
7. If it returns `needs_plan_revision`, do not route the comment directly to a code-fix worker. Before launching plan revision, create one failure-intake markdown record under `${WORKFLOW_FAILURE_INTAKE_ROOT}` using the structure in `failure_intake/README.md`. The record filename must include the source work item slug in lower kebab-case, such as `fea-123-ownership-boundary-missed.md` or `pln-456-compatibility-gate-missed.md`. Capture the work item slug, plan slug/id if present, PR URL, reviewer source, a short review-comment summary or brief quote, why the comment forced plan revision, the workflow phase where it should have been caught, the likely missing gate/reviewer/check, the generic failure class, proposed generic workflow hardening, codebase-specific details to ignore or abstract, status, and follow-up notes. The record describes a reusable workflow failure, not a repository-specific code bug or implementation recipe. Then launch a plan-revision subagent for the approved plan, passing the human review comment metadata, PR URL, current worktree path or paths, and current branch or branches. Tell the plan-revision subagent to invoke `$principal-engineer` when the human concern is about architecture, maintainability, module boundaries, ownership, abstraction quality, duplication, brittleness, or testability. The plan-revision subagent may inspect the current diff and relevant code to understand the concern, but it must not modify implementation code. It must revise the plan or return a concrete blocker/clarification request. Run a targeted plan-quality re-check over the changed plan sections and the human concern, including Principal Architecture re-check when `$principal-engineer` influenced the revision. For ClosedLoop-backed work items, create or reuse a planning manual loop for this post-PR plan revision following `sections/closedloop-manual-loop-visibility.md`. Record the planning loop evidence in the ledger. If code changes or PR replies are needed after the plan revision, create a separate PR follow-up loop before resuming or replacing the implementation/fix subagent.
8. If it returns `waiting_on_ci` or `waiting_on_review`, first verify its returned evidence satisfies Fresh PR Lifecycle Evidence for every PR latest head SHA. Record the current PR state, latest head SHA values, check summary, review-thread/comment summary, and returned `next_check_after` recommendation in JSONL and the ledger, then continue other work or end the turn. Do not reopen or reuse the execution loop for waiting. If a `pr_followup_loop_id` is active because a remediation pass is waiting for its post-fix build/check result, add a loop event with the waiting state and `next_check_after`; otherwise record waiting in JSONL only. Re-launch a bounded `post-pr-lifecycle` subagent only when the user resumes or asks for status, another workflow checkpoint is reached, CI/review state is known to have changed, or the recommended check time is reached during an already-active orchestration turn. If the user reports the PR merged while waiting, follow the Merged PRs End the Lifecycle Gate section instead of waiting for the next-check time or launching another lifecycle pass. If the bounded pass did not inspect review comments/threads, do not record `waiting_on_review`; treat that as incomplete evidence and rerun a targeted bounded pass or report `blocked`.
9. If it returns `blocked`, record the blocker in the ledger, report the blocker with evidence, and keep the work item open. If a `pr_followup_loop_id` is active and the blocker prevents the remediation pass from proceeding, call `fail_loop` with the blocker summary and verify terminal state with `get_loop`.
10. After the resumed implementation/execution subagent or replacement implementation-fix subagent returns, audit its returned packet before launching the bounded re-check. If any valid review comment was handled, the packet must include an `agents_rule_assessment` summary covering every valid review comment: the count assessed, counts by AGENTS.md decision (`updated`, `not_needed`, `blocked`), touched AGENTS.md paths with the commit SHA containing each update, notable exceptions, and `phase: agents_rule_assessment_completed` status-event evidence. If this evidence is missing, incomplete, or inconsistent with the handled comment count, resume the same fix subagent with a targeted blocker to complete or return the missing assessment. Do not infer the assessment yourself and do not proceed to PR-ready status.
11. After fixes are pushed, plan-revision alignment work is completed, review replies are posted, and AGENTS.md rule-assessment evidence is present when required, launch another bounded `post-pr-lifecycle` subagent with the active `pr_followup_loop_id` to inspect checks, review-thread state, reply placement, thread resolution state, draft/ready state, and AGENTS.md rule-assessment evidence. The orchestrator must not do that inspection directly.
12. Consider the work item complete when all PRs for that work item have a current bounded `post-pr-lifecycle` result of `ready_for_human_merge`, no manual testing debt is `unresolved` or `blocked_external`, and any tracked planning, execution, or PR follow-up loop for the work item has been verified terminal. If manual testing debt is `blocked_external`, report it as a concrete external blocker instead of marking the item complete. Before including the item as complete in final goal closeout, run `{{WORKFLOW_CLI}} gate --goal-slug <goal-slug> --work-item-id <work-item-id> --gate manual_loops_terminal` and `{{WORKFLOW_CLI}} gate --goal-slug <goal-slug> --work-item-id <work-item-id> --gate work_item_complete`. Ready for human merge means every GitHub check run, check suite, and status context for each PR's latest head SHA is terminal and non-blocking, except suites explicitly classified as inert app placeholders under this section; actionable review comments have been addressed or explicitly triaged; replies have landed in the correct threads; handled review threads are resolved where permissions allow; AGENTS.md rule-assessment evidence exists for every valid review comment addressed by this workflow; and workflow-required draft PRs have been marked ready for review. Do not treat "required checks passing" as sufficient when optional checks or review workflows are still pending, queued, requested, waiting, or in progress unless every non-terminal suite has been explicitly classified as an inert app placeholder with evidence.

Post-fix lifecycle re-checks must be launched from the runner and generated handoff packet: record the new PR head evidence, run `{{WORKFLOW_CLI}} next --goal-slug <goal-slug> --work-item-id <work-item-id> --write`, then run `{{WORKFLOW_CLI}} handoff --goal-slug <goal-slug> --work-item-id <work-item-id> --action launch_post_pr_lifecycle`. Do not hand-spawn a `post-pr-lifecycle` worker directly from this section when the runner can produce the action. Use the handoff packet's spawn policy exactly; the normal post-PR lifecycle policy is `gpt-5.5` with `reasoning_effort=high`, not `xhigh`.

Tell the bounded `post-pr-lifecycle` subagent:

1. Use the `status_file` path assigned by the orchestrator. Append status events there when starting, entering major phases, encountering blockers, and finishing.
2. If the orchestrator provides a `pr_followup_loop_id`, use ClosedLoop MCP `add_loop_event` for PR lifecycle pass start, returned PR state, blockers, and reply/thread audit outcomes for that active remediation pass. Do not create, complete, fail, or cancel manual loops. If no `pr_followup_loop_id` is provided, do not submit manual loop events for the inspection pass.
3. Perform exactly one inspection pass over every PR returned by finalization for this work item, then exit. Do not remain alive solely to poll GitHub.
4. Audit every GitHub check run, check suite, and status context for the latest head SHA of each PR, including optional checks, non-required checks, code-review checks, and automation such as Claude Code Review. Do not rely on `gh pr checks --required` or branch-protection status as the sole readiness signal. Return only the aggregate checks state plus failing or still-pending check names, not a per-check enumeration.
5. For every non-terminal check suite, decide whether it is a real waiting validation signal or an inert app placeholder suite. Classify a suite as `inert_app_placeholder` only when all of these hold: it comes from an installed GitHub App or integration rather than a concrete GitHub Actions workflow job; its `status` is `queued` or `requested` with null conclusion and zero check runs; it has no details, run, logs, or job URL or other inspectable run; it has been stale without check runs since creation while every real run-producing check run, suite, and status context for the same head SHA completed terminal and non-blocking; it is not required by branch protection, merge queue, rulesets, CODEOWNERS policy, or any required-check context; and no matching status context, check run, or repo-known validation provider indicates it hides a required build, test, deployment, review, or security signal.
6. Never classify a suite as `inert_app_placeholder` merely because it is optional, inconvenient, slow, or from a bot. Check runs, a details URL, a known validation purpose, branch-protection relevance, a recent update, or ambiguous requiredness make it a real non-terminal check: return `waiting_on_ci` or `blocked` with evidence.
7. If any check run, status context, or non-inert check suite is pending, queued, requested, waiting, in progress, or otherwise non-terminal, return `waiting_on_ci` with current check state and a `next_check_after` recommendation. Do not mark the PR ready while any real check is still running.
8. If any check has a terminal unsuccessful conclusion such as failure, cancelled, timed out, stale, startup failure, or action required, collect the failing check names, URLs, summaries, and relevant logs, then return `needs_fix` or `blocked` depending on whether the cause is repo-local or external.
9. Confirm all checks are terminal and non-blocking, or explicitly classified as inert app placeholders, and confirm manual testing debt is not `unresolved` or `blocked_external` before returning `ready_for_human_merge`. Success is the normal acceptable conclusion. Checks that GitHub marks skipped or neutral may be recorded as non-blocking only when they are terminal and clearly not hiding required validation.
10. Perform the full inert-placeholder audit for every ignored non-terminal suite, but return `inert_app_placeholder_suites` only as a count plus app name and one-line justification per classified suite, not per-suite field rows. If no suites are classified this way, return `inert_app_placeholder_suites: none`.
11. Inspect PR review comments, inline comments, requested-changes reviews, and unresolved review threads. Classify every review comment by reviewer source (`human`, `code-owner`, `bot`, `author`, or `unknown`) using GitHub author association, account type, app/bot metadata, review state, CODEOWNERS context when available, and reviewer identity evidence. Investigate each comment's URL, file/line context, reviewer text, thread resolution state, and actionability. Use classification and investigation only to compute the returned counts, escalation decisions, and lifecycle state; include specific comment URLs and short quotes only as blocker evidence for a non-ready conclusion, never as per-comment rows.
12. Human and code-owner review comments carry higher weight than bot comments. Bot comments can still be valid and actionable, but do not let a bot comment override or dilute a human/code-owner concern about architecture, maintainability, compatibility, security, product behavior, or implementation approach.
13. Treat broad human or code-owner concerns as possible plan defects, not routine patch requests. Comments using language such as "hack", "wrong abstraction", "not well thought out", "should be designed differently", "this breaks the model", "brittle", "overfit", "compatibility issue", "security concern", "wrong data model", "wrong ownership", or equivalent approach-level criticism must trigger a `$principal-engineer` review of the concern, approved plan, and affected diff/surface. Return `needs_plan_revision` unless that principal review provides strong source-backed evidence that the concern is purely local and can be fixed without changing the approved plan. Do not dismiss a broad human concern merely because it lacks a line-level replacement.
14. If a human or code-owner concern is too vague to revise the plan or code safely, return `blocked` or `waiting_on_review` with the exact clarification needed instead of guessing or treating the comment as invalid.
15. Audit every reply a fix subagent claims to have posted and every handled review thread. Fetch the PR review comments/threads and verify each claimed reply landed as a threaded reply to the original comment or thread (REST replies must carry `in_reply_to_id` equal to the original comment ID; GraphQL replies must appear in the expected `PullRequestReviewThread`; a top-level PR comment is not sufficient) and each handled resolvable thread is marked resolved. Set `replyPlacementAuditState` and `threadResolutionAuditState` to `passed` only when every claimed reply or resolution is verified, or `not_applicable` only when none was required.
16. If a claimed reply did not land as an actual threaded reply, a handled thread was not resolved when it could have been, or the subagent lacked permission to resolve it, return `needs_fix` or the exact permission blocker with the failing reply/thread metadata instead of trying to repair it directly.
17. If a previous fix subagent claimed review-comment handling, audit its `agents_rule_assessment` evidence. The evidence must show every valid review comment was assessed: assessed-comment counts consistent with handled comments, AGENTS.md decisions with touched paths and update commit SHAs where applicable, and `phase: agents_rule_assessment_completed` status-event evidence. If the assessment is missing, incomplete, or inconsistent with handled review comments, return `needs_fix` naming exactly which comments lack assessment. Do not mark a PR ready on the basis of code fixes and replies alone.
18. If the workflow, goal, or user instructions required draft PRs, ensure each PR is eventually switched out of draft state after all checks are terminal and non-blocking and actionable review comments are addressed. If the subagent lacks permission to mark a PR ready for review, return `blocked` with the exact permission or API blocker.
19. Return exactly one state: `ready_for_human_merge`, `needs_fix`, `needs_plan_revision`, `waiting_on_ci`, `waiting_on_review`, or `blocked`. If manual testing debt is `unresolved`, return `needs_fix` unless the only safe next step is plan revision. If manual testing debt is `blocked_external`, return `blocked` with the exact external dependency. Do not return `ready_for_human_merge` or `waiting_on_review` unless check runs, check suites, status contexts, inert-suite classifications, review comments, requested changes, unresolved threads, latest review activity, structured review counts, reply-placement audit state, thread-resolution audit state, and required AGENTS.md rule-assessment evidence were inspected for the latest head SHA. If `validReviewCommentCount` or `handledReviewCommentCount` is greater than zero, `agentsRuleAssessmentState` must be `passed` and `agentsRuleAssessmentMissingCount` must be zero before readiness. If comments, threads, checks, inert-suite classifications, audit states, or AGENTS.md assessment evidence could not be inspected because of auth, API, rate limit, permissions, tooling failure, or missing worker return data, return `blocked` or `needs_fix` with the exact inspection blocker instead of inferring from CI state.
20. Evaluate whether the PR lifecycle inspection revealed stable, source-backed, reusable, generalizable knowledge per `sections/lightweight-knowledge-capture.md`. If yes, write candidate note files under `${WORKFLOW_MEMORY_ROOT}/candidates/`; otherwise return `candidate_knowledge_notes: none` with a short reason. Do not write candidate notes for ordinary PR status.
21. Return a compact packet: the Fresh PR Lifecycle Evidence scalar set above, blocker text naming the specific failing checks, comments, threads, replies, or assessment gaps driving a non-ready conclusion, notable exceptions such as the `inert_app_placeholder_suites` summary and human/code-owner escalation decisions, any required fix inputs, `next_check_after` when waiting, PR follow-up loop event summary if a `pr_followup_loop_id` was provided, `candidate_knowledge_notes` with paths and summaries or `candidate_knowledge_notes: none` with a short reason, and whether user action is required. Perform every audit above in full, but do not transcribe per-check, per-suite, per-comment, or per-reply rows into the return packet. For non-ready conclusions, return the conclusion, blockers, and the evidence actually gathered, per Fresh PR Lifecycle Evidence.

Tell the resumed implementation/execution subagent, or the replacement implementation-fix subagent if the original cannot be resumed:

1. Use the `status_file` path assigned by the orchestrator. Append status events there when starting, entering major phases, encountering blockers, before long-running validation, and finishing.
2. Use the same worktree path or paths, branch or branches, and PR URL or URLs.
3. You are not alone in the codebase. Do not revert unrelated changes or edits made by others.
4. If the orchestrator provides a `pr_followup_loop_id`, use ClosedLoop MCP `add_loop_event` for fix start, validation start/completion, blockers, branch push, review replies, and fix completion. Do not create, complete, fail, or cancel manual loops.
5. Investigate only the failing GitHub check runs, check suites, status contexts, review comments, requested changes, unresolved review threads, user-reported manual regression, and code paths needed to fix them.
6. Give high value to human and code-owner review comments. A bot comment may still be valid, but a human/code-owner comment challenging architecture, maintainability, compatibility, security, product behavior, or implementation approach must not be dismissed without strong source-backed evidence. Invoke `$principal-engineer` for human/code-owner comments about architecture, maintainability, module boundaries, ownership, abstraction quality, duplication, brittleness, or testability. If the concern indicates the approved plan may be wrong or incomplete, stop and return `needs_plan_revision` evidence to the orchestrator instead of applying a superficial code patch.
7. If the issue is unrelated infrastructure, missing credentials, flaky external service, reviewer ambiguity, product disagreement, or another external blocker, report that with evidence instead of making speculative changes.
8. If a code fix is needed, patch the issue, add or update automated coverage that would have caught the failure when existing repo infrastructure supports it, rerun the relevant local validation plus any required full validation, commit a new fix commit, and push the branch without force.
