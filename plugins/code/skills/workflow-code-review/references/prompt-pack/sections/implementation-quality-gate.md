# Implementation Quality Gate

After the implementation `execution` subagent returns local implementation changes, the orchestrator must re-verify the Decision-Table Creation Gate from `sections/execution-phase.md` before launching implementation review.

Use the TypeScript batch runner for implementation review. It computes review-lane applicability from `execution.changedFiles` / `execution.reviewSurfaceManifest`, keeps core implementation lanes required, launches only applicable specialty lanes, and records `review.implementationLaneApplicability` when `{{WORKFLOW_CLI}} next --batch --write` is used. If changed-file evidence is missing or stale, the runner conservatively launches the existing broad lane set. An unknown changed-file category no longer forces the full lane set: each changed surface still routes to its lanes (core lanes always, specialty lanes on their signals), an unknown file additionally pulls principal-implementation and contract-security (security triage, fail closed), and automation-coverage-debt still runs when execution evidence triggers it. Each launched lane records `review.implementationReviewLanes.<laneId>` evidence. The orchestrator may aggregate implementation QA only after every launched lane is terminal with `pass`, `fail`, `blocked`, or `not_applicable`. Aggregation is ledger coordination only; the orchestrator must not inspect source code, patch code, align decision tables, or perform review work itself.

The orchestrator must not launch implementation review until the approved plan ID has a matching decision-table artifact path for every implementation worktree where code changes were made, the `execution-prep` subagent emitted a `decision_table_created` status event, and the orchestrator emitted `phase: decision_table_gate_verified`, `status: completed` before launching the implementation `execution` subagent. If this evidence is missing, mismatched, stale, or late, stop the work item and delegate remediation to the `execution-prep` subagent or a replacement prep subagent. Do not treat passing validation as a substitute for the decision-table gate.

The implementation `execution` subagent's first implementation/coding status event must occur after the orchestrator's `decision_table_gate_verified` event. If implementation/coding started before that event, the gate failed even if a matching artifact exists later.

If code was already written before the decision-table artifact existed or before the orchestrator verified the gate, the gate has failed. A remediation subagent may create a late alignment artifact and verify final code against the approved plan, but that does not retroactively satisfy the pre-coding gate. Report the skipped gate to the user as a workflow blocker and require explicit user acceptance before treating the work item as fully clean.

Before launching implementation review, the orchestrator must run:

```text
{{WORKFLOW_CLI}} gate --goal-slug <goal-slug> --work-item-id <work-item-id> --gate implementation_review_ready
```

If the gate fails, do not review or finalize the work item. The ledger must prove implementation completed, validation passed, and the decision-table creation gate passed for the approved plan.

The `implementation_review_ready` gate also requires structured execution self-audit evidence before any implementation-review lane can launch: `guardrailComplianceChecked/status`, `e2eUserFlowChecked/status`, `realBoundaryChecked/status`, `userVisibleStateMatrixChecked/status`, `manualTestingDebtChecked/status`, and no `executionBlockers`. If any of those fields are missing or blocked, resume the implementation subagent to complete the missing audit or resolve the blocker instead of asking review lanes to infer it. Exception: when `WORKFLOW_VISUAL_QA_ENABLED=true`, `manualTestingDebtStatus="blocked_external"`, and the manual-smoke debt is specifically for rendered browser, Electron, or shared-UI visual surfaces, the runner should route `run_visual_qa` before asking a human to provide manual smoke evidence.

Each implementation-review lane subagent must:

1. Use the `status_file` path assigned by the orchestrator. Append status events there when starting, entering major phases, encountering blockers, and finishing. The final JSONL event must include terminal lane evidence with `laneId`, `status: pass|fail|blocked|not_applicable`, `completedAt`, `findings`, `blockers`, and `evidenceSummary`, either nested under `laneEvidence` or at top level. After the subagent returns, the orchestrator must run `{{WORKFLOW_CLI}} lane --goal-slug <goal-slug> --work-item-id <work-item-id> --kind implementation --lane-id <lane-id> --status-file <status_file>` before rerunning `{{WORKFLOW_CLI}} next`.
2. Use the same worktree path or paths and branch or branches returned by the execution subagent.
3. If the orchestrator provides an `execution_loop_id`, use ClosedLoop MCP `add_loop_event` for implementation-review start, findings, pass, or blocker outcomes. Do not create, complete, fail, or cancel manual loops.
4. Use the lane applicability reason from the handoff as the assigned scope boundary. If the changed files reveal a high-risk surface that the applicability manifest missed, return a blocked lane with that mismatch instead of broadening into an unassigned lane.
5. Be read-only. Do not modify files.
6. Inspect the approved plan URL, the matching decision-table artifact for the approved plan ID, the full local worktree diff, repo guardrails, the execution subagent's guardrail compliance audit, and validation results. Fail the review if the artifact is missing, uses another plan ID, was created after coding started, or appears to be a stale artifact from another work item.
7. Include untracked files in review scope. Inspect `git status --short --untracked-files=all`, review all relevant tracked and untracked source/test files, and state whether any untracked files are ignored, irrelevant, generated, or required for the implementation. Do not rely on the execution subagent's decision-table closeout as proof that the full worktree was reviewed.
8. Perform an explicit Guardrail Compliance Pass before marking the implementation review as passed:
   - Read every applicable guardrail file for the changed paths, including root `AGENTS.md`, nearest path-specific `AGENTS.md`, `CLAUDE.md`, and files referenced by those guardrails.
   - Verify the execution subagent returned a guardrail compliance audit and emitted `phase: guardrail_compliance_checked`. Missing audit evidence is a review failure.
   - Build a changed-file to guardrail-rule matrix and check the final tracked and untracked diff against each applicable rule. Do not treat `/review`, tests, typecheck, lint, or build as substitutes for this pass.
   - Check repo-specific conventions literally, including enum/type constant usage in fixtures, validation of raw database or external values before casts, logging assertion bans, telemetry/log key naming, unused parameters or churn, generated-file rules, documentation/comment rules, and any other applicable guidance.
   - Any violation must be returned as an actionable finding with the violated guardrail file/rule, changed file/line, exact failure mode, and required correction.
   - For every valid guardrail, convention, type-safety, generated-file, validation, or static-safety violation, perform a Guardrail Automation Gap Assessment. Classify the miss as `already_automated_but_failed`, `automatable_now`, `docs_only_rule`, or `not_automatable`. If existing lint, typecheck, schema validation, code generation, test, formatter, or repo-supported static tooling can enforce it, the required correction must include adding or updating that automation instead of only documenting the rule. If automation is not practical, explain why and identify the narrowest durable guardrail documentation that would help future reviewers.
9. Perform a conditional E2E/User-Flow Validation Pass before marking the implementation review as passed:
   - Apply the E2E/User-Flow Test Applicability definition from `sections/planning-phase.md`.
   - Apply the Real Boundary Scenario Coverage definition from `sections/planning-phase.md`.
   - If a command exercises a running app, dev server, service, or other runtime dependency (for example E2E, browser, or smoke commands), get a correctly bound runtime before running it. First check whether a usable instance is already running for this target. If one is running, verify it actually serves THIS work item's worktree, branch, and current build before reusing it (something answering on the expected port is not proof of the right build), and reuse it without restarting when it is correct. If it serves a different worktree, branch, or stale build, do not run against it: bring up an instance bound to this worktree instead, and if a conflicting instance prevents that, report a blocker rather than running against the wrong one. If nothing is running, start it. Workflow does not define how to detect, verify binding, isolate per worktree, or start any project's runtime: consult the injected `Relevant repo memory` block and repo-provided launch/setup docs for those procedures, and when that block is missing or empty query workflow memory for the target repo first (for example `workflow-memory query --repo <repoName> --action launch_implementation_review_lane --query "dev server start launch run e2e smoke port auth"`). Starting a runtime is permitted even in an otherwise read-only or validation pass; leave any generated build/runtime artifacts untracked and unstaged and do not commit them. If the runtime cannot be brought up or correctly bound with existing repo-provided tooling, report the missing runtime setup as a blocker rather than assuming the app is up or recording an environment gap as a code failure.
   - If the final diff changes a user-visible workflow, critical integration path, browser/client flow, command flow, onboarding/launch/setup path, upload/download path, checkout/payment path, or multi-step API/client sequence, verify the approved plan included an E2E/User-Flow Test Applicability decision.
   - If the final diff changes a multi-step materialization, projection, rendering, route/API response, persisted shape, migration, compatibility alias, async/background recovery path, optional relationship behavior, feature flag behavior, or other producer-to-consumer contract where isolated mocks could hide drift, verify the approved plan included a Real Boundary Scenario Coverage decision.
   - Inspect existing E2E/user-flow infrastructure, commands, fixtures, and nearby examples in the affected repo or relevant configured repo.
   - If existing E2E/user-flow infrastructure is present and the behavior is best validated through the real user/client path, verify the implementation added or updated the required E2E/user-flow test and ran the relevant command, or return an actionable missing-test finding.
   - Inspect existing integration, route, smoke, browser, CLI-flow, migration, or scenario-test infrastructure for the affected producer-to-consumer boundary. If existing infrastructure is present and isolated mocks could hide drift, verify the implementation added or updated a real-boundary scenario test or bounded test chain and ran the relevant command, or return an actionable missing-test finding.
   - If an E2E/user-flow test claims a user-facing element is visible, onscreen, centered, scrolled into view, or inside the viewport, verify the test asserts the visual viewport state using existing repo tooling, such as screenshot evidence, screenshot diff, bounding box versus viewport bounds, intersection ratio, or another repo-approved visual check. Accessibility tree state, locator presence, DOM attachment, role lookup, or DOM-level visibility alone is not sufficient and must be returned as an actionable missing-assertion finding.
   - For UI layout, styling, or visual rendering changes, verify the implementation includes rendered-screen evidence from existing repo tooling or a repo-grounded manual-testing-debt classification. Return an actionable finding for obvious layout regressions or missing coverage: overlapping elements, clipped/unreadable content, misplaced anchored content, broken scrolling, responsive viewport breakage, unrealistic-only fixtures, or accidental debug/demo/test copy and temporary markers.
   - For materialization/projection/rendering pipelines, verify coverage crosses real input or event -> persisted/materialized state -> production route/projection/API/tool shape -> consumer rendering or usage, or verify a repo-grounded reason that isolated tests are sufficient.
   - For anchored or positional UI behavior, verify the final diff preserves the approved source-to-renderer anchor mapping and tests prove attachment to the intended row, line, range, coordinate, timestamp, source item, or equivalent location instead of merely proving the item exists somewhere in the UI.
   - For externally observed automatic resource creation, materialization, linking, claiming, or storage, verify the implementation follows the approved ownership-resolution matrix for events with and without the primary routing identifier, including no-match, ambiguous-match, stale-match, nullable-owner, and partial-owner outcomes when those states are possible.
   - For migrations that change persisted shapes consumed by routes, projections, tools, clients, or renderers, verify post-migration smoke or route/projection validation against realistic legacy or migrated data where existing infrastructure supports it.
   - For migrations, projection cutovers, compatibility backfills, source-of-truth moves, old/new path coexistence, or batch repairs, verify the implementation follows the approved Cutover, Backfill, And Compatibility Matrix. Tests or validation must prove old/new path agreement, scoped backfill correctness, complete iteration or pagination behavior, retry/idempotency behavior, tombstone or soft-delete handling, ambiguous-match handling, mixed-version compatibility, and required guardrail automation or reviewer checks. Return a plan-gap finding if the approved plan omitted the matrix or left those decisions to execution.
   - For deprecated aliases, compatibility routes, legacy payloads, or fallback inputs, verify legacy input flows into the new canonical storage/output and remains visible through downstream canonical consumers.
   - For async/background/cache/wait/retry/recovery paths, verify failure injection, recorded stale/failure/partial state, retry/sync/recovery invocation, and recovered state or response when existing infrastructure supports it.
   - For multi-step sync, refresh, import, reconciliation, repair, batch update, background job, external-provider fanout, or workflow operations with independently failing sub-operations, verify the implementation follows the approved Multi-Step Failure-Mode Matrix. Tests must prove sub-operation independence, throttle scope, skipped/stale/partial/total failure behavior, independent continuation after local failure, degraded-success response or persisted-state semantics, retry/resume/terminal behavior, and absence of dead or unreachable branches. Return a plan-gap finding if the approved plan omitted the matrix or left those decisions to execution.
   - For optional child, nullable relationship, or missing related data behavior, verify boundary tests cover the intended null/empty/default shape and no production 500/serialization failure.
   - For feature-flag behavior, verify flag-on and flag-off coverage uses the same persisted fixture or scenario data at the highest existing practical boundary when such a boundary exists; mocked component-level flag values alone are not sufficient in that case.
   - If no existing E2E/user-flow infrastructure or pattern exists, state that explicitly with evidence and do not ask for a new framework or broad test architecture.
   - If no existing real-boundary scenario infrastructure or pattern exists, state that explicitly with evidence and require only the next-best existing validation level.
   - For final diffs that expose new or changed related data, metadata, derived fields, or projections, verify the implementation follows the approved Exposure Surface Parity Matrix. Tests must prove parity across equivalent read surfaces and caller classes, excluded consumers remain excluded, serialized null/empty/default/date/status behavior is stable, telemetry/log scope is correct, raw or external values are validated before casts or exposure, and fixture builders produce realistic supported shapes. Return a plan-gap finding if the approved plan omitted the matrix or left any of those decisions to execution.
   - For final diffs that add or change mutation actions, commands, write endpoints, workflow operations, or state-changing tools, verify the implementation follows the approved Mutation Contract Matrix. Tests must prove compatibility for existing callers, correct success and failure envelopes, target and ownership validation, read-after-write visibility through every intended read path, idempotency or retry behavior, partial-apply handling, and structured input boundary cases. Return a plan-gap finding if the approved plan omitted the matrix or left those decisions to execution.
   - For final diffs that create, promote, canonicalize, or materially change a first-class resource, lifecycle object, durable state record, or externally refreshed entity, verify the implementation follows the approved Stateful Resource Compatibility Matrix. Tests must prove required identity propagation, read/write surface alignment, durable-state preservation when updates are partial or stale, partial external failure behavior, nullable migration-window behavior, and consumer-visible compatibility. Return a plan-gap finding if the approved plan omitted the matrix or left those decisions to execution.
   - For user-visible state/status/lifecycle/rendered output derived from multiple sources, verify the approved plan and implementation include a User-Visible State Matrix. The implementation must cover initial load before user action, refresh/retry/repair behavior, stale or mixed field combinations, precedence rules, final rendered or consumer-visible output, and the actual renderer/consumer when existing infrastructure supports it. Tests that mock away the final renderer/consumer are insufficient unless the lane records a repo-grounded reason the lower boundary is the highest practical coverage.
   - If the plan omitted the applicability decision, omitted the Real Boundary Scenario Coverage decision, omitted the User-Visible State Matrix when required, omitted the External Observation Ownership Resolution matrix when required, omitted the visual viewport assertion requirement for viewport visibility claims, or left test level to execution when repo context can resolve it, return a plan-gap finding rather than silently passing the implementation.
10. If assigned the `automation-coverage-debt` lane, perform a dedicated Manual Testing Debt Pass before marking the lane passed:
   - Apply the Manual Testing Debt Classification definition from `sections/planning-phase.md`.
   - Inspect the approved plan, decision table, validation results, final diff, PR body draft if available, and test infrastructure for manual testing, manual verification, live-provider checks, staging-only checks, webhook replay, real identity checks, provider-bound checks, or equivalent validation debt.
   - If existing E2E/user-flow, real-boundary, route, integration, smoke, CLI-flow, browser, or component-test infrastructure can cover the behavior, return an actionable missing-test finding instead of accepting manual validation.
   - If manual validation remains, verify every item is classified as `none`, `automated`, `justified`, `blocked_external`, or `unresolved`, includes the reason, and names the highest practical automated substitute plus validation command when one exists.
   - Treat vague statements such as "manual verification still needed" as `unresolved` unless classified with evidence.
   - Return `blocked_external` only for concrete external-system, credential, staging-only, webhook-delivery, permission, or unavailable-upstream blockers; do not use it for avoidable missing automation.
11. Perform a conditional Database/Migration Safety Pass before marking the implementation review as passed:
   - Apply the Database/Migration Safety definition from `sections/planning-phase.md`.
   - If the final diff changes ORM schema, migration files, raw SQL, generated database clients/types, persisted models, indexes, constraints, foreign keys, unique constraints, backfills, seed data, or data consumed by persisted projections, verify the approved plan included a Database/Migration Safety decision.
   - Verify the execution subagent returned a Database/Migration Safety execution summary and emitted `phase: database_migration_safety_checked`. Missing audit evidence is a review failure for database/migration-sensitive diffs.
   - Inspect every changed schema file, migration file, raw SQL file, generated database client/type file, and backfill/seed script in the final tracked and untracked diff.
   - Determine whether each migration is generated, hand-authored, or edited after generation. If SQL is hand-authored or edited after generation, verify the repo-grounded rationale and exact invariants are documented.
   - Verify every changed index, unique constraint, foreign key, relation, default, enum, trigger, and extension matches ORM/schema expectations or explicit schema mappings. Functional migration success is not enough when constraint/index/FK names can drift from ORM metadata.
   - Verify repo-supported ORM drift validation passed when available, such as a shadow-database drift check for Prisma-style repos. Deploy/apply-only validation is insufficient for ORM-managed schema changes.
   - Verify migration apply/deploy validation passed when applicable, and verify pre-existing-data, duplicate, null, orphan, backfill, idempotency, rollback, and downstream post-migration validations required by the plan.
   - If the repo lacks a safe local drift validation path, return an actionable blocker or human-acceptance requirement instead of passing on deploy/apply evidence alone.
   - Return actionable findings for constraint-name mismatches, ORM metadata drift risk, missing drift validation, missing generated-client/schema validation, unsafe hand-authored SQL, missing pre-existing-data checks, or missing downstream post-migration validation.
12. In the `principal-implementation` lane, run a Principal Implementation Review using `$principal-engineer` unless the final diff is docs-only, copy-only, fixture-only, generated-only, or a purely mechanical one-file change with no changed abstraction, boundary, or ownership decision.
   - Inspect module boundaries, ownership fit, route/component/service responsibility split, duplication, abstraction quality, typed boundary contracts, hardcoded strings versus existing constants/enums, unnecessary casts, testability, hidden coupling, and whether tests cover the behavior risk rather than implementation trivia.
   - Classify each issue as `Fix now`, `Ask first`, `Follow-up`, or `Ignore`.
   - Treat `Fix now` findings as actionable implementation-review findings when they are directly in touched code, low risk to correct, and would make the current change safer, less brittle, easier to test, or more consistent with existing repo ownership.
   - Treat `Ask first` findings as blockers requiring user or architecture decision before finalization.
   - Do not block finalization on `Follow-up` or `Ignore` findings, but return them in a concise Principal Review section.
13. Run `/review` if available for the assigned lane and scope. If `/review` is unavailable, perform a code-review-style pass focused on the lane's assigned risks: correctness, regressions, missing tests, contract drift, repo guardrail violations, decision-table mismatches, E2E/user-flow applicability misses, real-boundary scenario coverage misses, database/migration safety misses, or principal-review findings.
14. Evaluate whether the review revealed stable, source-backed, reusable, generalizable knowledge per `sections/lightweight-knowledge-capture.md`. If yes, write candidate note files under `${WORKFLOW_MEMORY_ROOT}/candidates/`; otherwise return `candidate_knowledge_notes: none` with a short reason. Do not write candidate notes for ordinary review status.
15. Return lane evidence with findings ordered by severity, file/line references, exact failure mode, evidence, whether each finding is actionable, lane-specific validation details, and `candidate_knowledge_notes` with paths and summaries or `candidate_knowledge_notes: none` with a short reason. The lane must not declare the full implementation quality gate passed.

The orchestrator must triage review findings through the workflow runner, not by locally reading code:

- As soon as any implementation-review lane returns `fail` or `blocked`, record its compact finding artifact path in `review.remediation.findingArtifactPaths` and run `{{WORKFLOW_CLI}} next --goal-slug <goal-slug> --work-item-id <work-item-id> --batch --write`.
- If the runner returns `start_remediation_worker`, launch exactly one remediation worker for the queued artifact paths while other already-running review lanes continue.
- If additional lane artifacts arrive while that worker is active, use the runner-provided `append_remediation_findings` action to send only the new artifact paths to the same worker. Do not start parallel fixers for overlapping review findings.
- Only after the remediation worker completes and all review lanes are terminal does the runner emit typed targeted re-check lane actions: `launch_implementation_review_lane` with `reviewLaneScope: "targeted_recheck"` for each previously failed or blocked lane whose evidence predates the remediation completion. Dispatch each via its runner-provided handoff command. Ingest each re-check with `{{WORKFLOW_CLI}} lane --goal-slug <goal-slug> --work-item-id <work-item-id> --kind implementation --lane-id <lane-id> --status-file <status_file>` before rerunning `{{WORKFLOW_CLI}} next`. When every re-check lane returns fresh passing evidence, the runner emits the plain `aggregate_implementation_review` action; run `{{WORKFLOW_CLI}} review aggregate --goal-slug <goal-slug> --work-item-id <work-item-id> --kind implementation` to derive the gate pass from lane evidence (direct QA-pass field upserts are still rejected, and the aggregate refuses while affected lanes lack post-remediation evidence). If a fresh re-check still fails with a new finding artifact, the runner starts a second remediation round via `start_remediation_worker`. If a fresh re-check still fails and nothing new is pending, the runner emits a blocked action requiring a human decision via `{{WORKFLOW_CLI}} remediation resolve --decision <waived|rerun> --reason <text>`. From this completed-remediation state, `rerun` clears the completed status and re-queues the acknowledged findings so the runner starts a fresh remediation round (`start_remediation_worker`); `waived` records the waiver and restamps staleness forward so the runner emits one final targeted re-check whose worker honors the recorded waiver (it does not re-flag the waived findings and records the lane pass/not_applicable when only waived findings remain). `aggregate_remediation` is recognized for backward compatibility but is no longer emitted.
- Valid and actionable findings: route them through the remediation worker/action above.
- Unclear findings: ask the user before changing code.
- Invalid or not applicable findings: record the reason and do not patch.
- Missing or incomplete review evidence: do not fill the gap by reading code directly. Launch a targeted re-check subagent with the missing scope, such as "include untracked files and verify decision-table alignment against the full worktree", "perform the Guardrail Compliance Pass against AGENTS.md/CLAUDE.md for every changed path", "perform the E2E/User-Flow Validation Pass against existing repo infrastructure and the changed user/client path", or "perform the Real Boundary Scenario Coverage pass against the changed producer-to-consumer contract."
- Missing or incomplete database/migration evidence: launch a targeted re-check subagent with the missing scope, such as "perform the Database/Migration Safety Pass against changed schema/migration/raw SQL files, verify ORM expected constraint/index/FK names, and verify drift/apply/downstream validation evidence."
- Missing or incomplete manual testing debt evidence: launch a targeted `automation-coverage-debt` re-check subagent. If the debt is rendered browser, Electron, or shared-UI smoke evidence and `WORKFLOW_VISUAL_QA_ENABLED=true`, let the runner schedule `run_visual_qa` before asking for a human waiver or manual smoke-test result. Auth/login blockers on a rendered browser or Electron surface are eligible for visual QA, which may record `AUTH_REQUIRED` or `INCOMPLETE_DOCS`; non-rendered credential/login setup is not. Do not use visual QA for unrelated external blockers such as provider delivery, webhook replay, reviewer permissions, staging-only upstream systems, non-rendered credentials/login setup, or non-UI database/API validation. Do not let the orchestrator decide whether manual testing is acceptable by reading code directly.
- Missing or incomplete Guardrail Automation Gap Assessment: launch a targeted guardrail-compliance re-check subagent. Do not accept guardrail findings that only say to fix the instance when existing repo automation could prevent recurrence.
- Principal Review `Ask first` findings: ask the user before changing product behavior, public contracts, schema, migrations, broad module boundaries, or risky abstraction choices.
- Principal Review `Follow-up` findings: record them in the work-item summary or candidate knowledge only when they are stable and source-backed; do not patch them in the current workflow unless the user explicitly approves.

If a fix subagent is needed, tell it:

1. Use the `status_file` path assigned by the orchestrator. Append status events there when starting, entering major phases, encountering blockers, before long-running validation, and finishing.
2. Use the same worktree path or paths and branch or branches.
3. If the orchestrator provides an `execution_loop_id`, use ClosedLoop MCP `add_loop_event` for fix pass start, validation start/completion, blockers, and fix completion. Do not create, complete, fail, or cancel manual loops.
4. You are not alone in the codebase. Do not revert unrelated changes or edits made by others.
5. Address only the approved actionable review findings.
6. Update the decision-table append-only sections if the fix changes behavior or closes verification drift.
7. If the fix addresses E2E/user-flow, real-boundary scenario, or automation-coverage-debt findings, use existing repo infrastructure, commands, fixtures, and patterns only. For viewport visibility findings, add visual viewport evidence rather than replacing one DOM/accessibility assertion with another. For real-boundary scenario findings, test the real producer-to-consumer contract or bounded chain instead of adding another fully mocked unit test. Do not introduce a new E2E framework, new scenario-test framework, or broad test architecture unless the user explicitly approves it.
8. If the fix addresses database/migration findings, preserve ORM/schema expectations. Prefer regenerating migrations or aligning schema mappings over hand-renaming SQL unless the repo requires hand-authored SQL. Rerun drift validation, apply/deploy validation, and affected downstream post-migration validation.
9. Rerun affected validation plus any required full validation, including affected E2E/user-flow, real-boundary scenario, database drift, migration apply/deploy, and downstream post-migration validation when the fix added or updated those tests or migrations.
10. Do not commit, push, open a PR, or notify the user that the PR is ready.
11. If the fix addresses Principal Review findings, keep the fix scoped to the approved `Fix now` findings. Do not expand into `Follow-up` cleanup or broad refactors without explicit user approval.
12. Evaluate whether the fix work revealed stable, source-backed, reusable, generalizable knowledge per `sections/lightweight-knowledge-capture.md`. If yes, write candidate note files under `${WORKFLOW_MEMORY_ROOT}/candidates/`; otherwise return `candidate_knowledge_notes: none` with a short reason. Do not write candidate notes for ordinary fix status.
13. Return changed files, validation results, loop event summary if applicable, E2E/User-Flow fix summary if applicable, Real Boundary Scenario Coverage fix summary if applicable, Database/Migration Safety fix summary if applicable, Principal Review fix summary if applicable, `candidate_knowledge_notes` with paths and summaries or `candidate_knowledge_notes: none` with a short reason, and whether any blocker remains.

After the fix subagent finishes, launch a targeted re-check subagent to verify only the addressed findings and any changed validation surface. If an `execution_loop_id` exists, pass it to the targeted re-check subagent and instruct it to use `add_loop_event` for re-check start and result. The targeted re-check subagent must also return `candidate_knowledge_notes` with paths and summaries or `candidate_knowledge_notes: none` with a short reason per `sections/lightweight-knowledge-capture.md`.

Do not run infinite review/fix loops. Allow one full independent review, one fix pass, and one targeted re-check. If the targeted re-check still finds serious issues, the runner emits a blocked action; use `{{WORKFLOW_CLI}} remediation resolve --decision <waived|rerun> --reason <text>` to require a human decision before proceeding. Both decisions are accepted from the completed-remediation state only while re-checks still fail (or deferred findings/blockers remain): `rerun` starts a new remediation round; `waived` triggers one final targeted re-check that honors the recorded waiver.

When every required implementation-review lane is terminal, run `{{WORKFLOW_CLI}} review aggregate --goal-slug <goal-slug> --work-item-id <work-item-id> --kind implementation`. The command derives the gate outcome from the recorded lane evidence: it records `review.implementationQaPassed`, `review.implementationQaAt`, and `review.unresolvedFindings` itself, refuses while required lane evidence is missing or a remediation is active/blocked/unacknowledged, and records a failed aggregate (with unresolved findings) when any lane is still fail or blocked. Direct ledger upserts of the QA-pass fields are rejected; previously failed lanes need fresh passing re-check lane evidence before the aggregate can pass.

After updating the ledger, run:

```text
{{WORKFLOW_CLI}} gate --goal-slug <goal-slug> --work-item-id <work-item-id> --gate final_workflow_review_ready
```

If the gate fails, do not launch final workflow-code-review until the missing or blocking implementation QA evidence is corrected.
